Desired behavior / design to evaluate:
1. Separate LOOP PROTECTION from OUTPUT LENGTH.
   Loop protection should be based primarily on evidence of no progress, for example repeated identical/similar tool calls, repeated same error, repeated state with no new evidence, excessive retries on the same action, or another robust progress detector. Productive reading, diagnosis, writing reports, and moving through different nodes should not trip the loop guard merely because many tokens are generated.

2. Normal productive work should not be terminated just because it reaches an arbitrary 10K/32K generated-token count.
   If the local model/harness can truly use unlimited generation safely, consider removing the artificial cap for autonomous work.
   If some finite per-turn limit is structurally required, make it large enough for safety and treat reaching it as a CHECKPOINT, not task completion.

3. If a productive turn reaches a hard technical max-output boundary:
   - persist state/checkpoint first;
   - do NOT mark the bridge job COMPLETE;
   - automatically continue the SAME task/session from that checkpoint;
   - preserve the original job goal and safety constraints;
   - only stop when Ornith explicitly concludes the task is complete, hits a real safety/decision boundary, encounters an unrecoverable error, or the loop guard determines genuine no-progress behavior.

4. Bridge completion semantics:
   reason=max-tokens must never by itself map to state: COMPLETE.
   Prefer an explicit state such as CONTINUE/CHECKPOINT/RUNNING if the bridge supports it, or otherwise suppress the final result until the continuation chain actually completes.

5. Keep loop protection strong.
   Please do not solve this by simply disabling every guard. We still want protection from runaway loops, repeated destructive actions, repeated SSH/tool failures, and meaningless self-repetition. The goal is to remove the OUTPUT-LENGTH-as-stop-condition, not the safety/no-progress guard.

6. File-first long work:
   For long forensic jobs, encourage Ornith to write detailed analysis/evidence continuously to the requested report/log files and keep bridge/chat summaries compact. This reduces context/output pressure, but it should be an efficiency strategy, not a requirement that can stop useful work.

7. Preserve current safety policy for the Storj recovery:
   no format/wipe/recreate/delete of volumes or node data; evidence before changes; destructive/ambiguous storage actions require STOP + SUPERVISOR SUMMARY with decision_needed: yes.
