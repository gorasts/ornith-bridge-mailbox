2. TURBOPREFILL — WHAT THE CODE ACTUALLY DOES
From saved source artifact tp_core_code.txt:

Normal llama.cpp layer split was effectively too serialized. TurboPrefill changes prompt processing into an ubatch-level diagonal/wavefront pipeline so different Vegas can work on different ubatches/stages concurrently.

Recovered implementation details:
- capture_turboprefill_ub(...) snapshots each UB’s scheduler state.
- Saved state includes:
  - split graphs
  - tensor metadata
  - live input banks
  - intermediate banks
  - input plans
  - per-split metadata indexes
- Explicit phases:
  - TP_PHASE_PREPARE_H2D
  - TP_PHASE_COMPUTE
  - TP_PHASE_STORE
- Split 0 is run/captured first; diagonal replay begins at split 1 when possible.
- GPU/backend events are created for:
  - compute_done
  - d2h_done
  - h2d_ready
- Dependencies are preserved by synchronizing the required prior D2H before H2D of dependent split input.
- Intermediate host storage preferentially uses a 256-byte-aligned pinned arena, falling back to ordinary vectors if pin allocation fails.
- Before replay, current tensor metadata and live scheduler split snapshots are captured.
- After TurboPrefill replay, original scheduler state is restored.
- The scheduler logs:
  turboprefill: version=... accumulation_us=... compute_us=... total_us=...
- The saved UB series is cleared and the pinned arena compacted after completion.

This is genuine concurrent three-card prompt-processing work, not just rapid sequential alternation.
