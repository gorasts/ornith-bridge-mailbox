## Finding and next diagnostic

The measured COMPUTE windows were almost entirely inside host time in `ggml_backend_graph_compute_async`, while event-wait API time was negligible. Existing backend synchronization accounted for about 0.677 s, material but smaller. This does **not** establish that the graph-call time is CPU encoding, a hidden wait, or GPU execution. The meaningful bottleneck is therefore narrowed to long per-device Vulkan graph-compute host calls plus explicit backend synchronization, with the split between host submission and device work still unknown. No optimization lever is justified yet.

The smallest useful next diagnostic would add device-side timestamps around the already-submitted per-device graph work and read them only at the existing end-of-series synchronization, then compare device elapsed time with these host-call intervals. Do not enable the existing Vulkan performance logger for this purpose: its path adds a fence wait and changes timing. No follow-up was run or queued.
