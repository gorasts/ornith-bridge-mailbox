## ASUS88: Linux alternatives tested

- The node is stopped and drive88 is unmounted. Boot metadata was preserved under `/root/sol-storj-fsrepair-20261016` on ASUS.
- `ntfsfix -n` exits0: the basic MFT/MFTMirr and boot-sector checks pass. That does not validate all directory indexes.
- The original ntfs3 driver returns invalid-argument errors on specific piece paths. The alternative ntfs-3g driver was tested read-only; the same paths return input/output errors. A driver switch did not resolve the fault.
- `ntfsrecover -n -v` exits1 and reports: **The log file has been wiped out**. There is no surviving journal for that Linux tool to replay. No journal replay or forced dirty-flag clearance was performed.
- `ntfsinfo` reports the volume is scheduled for a check. SMART access through the present USB bridge did not succeed, so physical health of88 is not established.
- The remaining task is full NTFS structural/index repair, with Windows chkdsk a known supported route. The available Linux checks/recovery tools did not fix this fault. Rebooting ASUS or moving its disk was not silently undertaken because other healthy nodes use that computer.

The upstream [ntfsfix documentation](https://github.com/tuxera/ntfs-3g/blob/edge/ntfsprogs/ntfsfix.8.in) distinguishes its limited fixes from a full consistency check. [ntfsrecover](https://github.com/tuxera/ntfs-3g/blob/edge/ntfsprogs/ntfsrecover.8.in) replays surviving Windows transactions; it cannot reconstruct a wiped log.
