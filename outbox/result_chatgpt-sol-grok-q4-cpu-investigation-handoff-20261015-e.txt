# Independent Q4 CPU-pipeline advice — 15 October 2026

I read all four requested original reports and `docs/SUPERVISOR_RULES.md` from mailbox main at commit `f86fbf4c14bbf8008aaa26261b1e04595426d356`. I also retrieved the current CPU, Vulkan and scheduler source read-only. All three source SHA256s exactly match Stage 0. I made no engine changes, compiled nothing, launched no tests and changed no remote service or hardware state for this advisory. Report publication is the only repository change.

**Recommendation: defer the depth-4 cap and further lifetime patches. Authorize one controlled observational stage that joins each worker wait to its actual Vulkan queue submission, with instrumentation confined to prefill. The proposed required-value/current-value trace is useful but insufficient without that submission provenance.**

This advice concerns Ornith Q4 on Vulkan in `/home/ubuntu/c1-xdev`. It does not concern the separate Strata HIP/ISTA IQ3_S experiments. No performance or correctness result transfers between them.

## 1. Ranked diagnosis

### Confirmed by the reports and matching source

1. **The drains predominantly wait for GPU inputs.** Stage 1 attributes 18.397/25.010 seconds (73.6%) and 18.727/24.044 seconds (77.9%) to semaphore waits. CPU multiplication takes 5.326 and 4.423 seconds in those windows and actually uses about 14 CPU threads. This rules out “the whole 25-second drain is one slow CPU matmul.” It does not prove which producer dependency delays the signal. The source confirms the single dispatch worker waits, copies inputs, releases staging slots, computes, then publishes outputs. [S1; CPU lines 307–386]

2. **The current narrow path has incomplete input retirement.** Inputs are registered under `submitted + 1`; narrow inline compute does not submit that ticket or execute its input callbacks. Ordinary successful D2H slots are released by those callbacks. The observed full pool with zero releases is consistent with this source defect. Stages 2 and 3 remove the observed leak under their respective paths, but neither establishes whole-engine correctness. [S0–S3; CPU 596–638; Vulkan 17110–17119, 17181–17257]

3. **A call to `ggml_vk_submit()` is not evidence of actual queue submission.** The wrapper returns early after putting a context in `vk_parked` when parking is enabled (Vulkan 3172–3178). Actual queue submission is at 3253. Mode 0 flushes held contexts; mode 2 permits new work to submit while leaving older parked contexts in the list (3261–3284). The scheduler chooses mode 2 for a qualifying non-CPU prefix (backend 2175–2195). This is the most important refinement to the handoff's assertion that copies were “submitted ahead” of the worker.

4. **The long checkpoint pause is predominantly synchronization, not state copying.** The measured 65,864,428-byte copy takes 132 ms after the 24.044-second drain. Moving or removing the checkpoint drain cannot be credited as a speedup unless total request time falls and checkpoint semantics remain correct. [S1]

5. **The measured pipeline benefit remains marginal.** The same-placement 16K ON/OFF pair is 302.869 versus 299.318 PP; total prompt time is nearly unchanged when waits move between D2H and checkpoint barriers. There is no demonstrated material PP win or sustained TG512 win. [S0]

### Strong inferences, not yet proven failures in every output

- **The baseline may consume stale input, not merely leak slots.** In the narrow path the deferred host memcpy is not executed by a matching worker ticket before inline compute. Unless another valid path already materialized that destination, compute has no demonstrated fresh-input guarantee. Later synchronous fallback can mask this defect and make the baseline look fast or coherent. This is a correctness risk; I cannot assign each observed token divergence to it from these artifacts alone.
- **Head-of-line blocking or delayed submission could explain part of the wait.** One worker waits on its current job even if independent later inputs might be ready. Parked producers and GPU/CPU dependency chains also offer explanations. Neither a dependency cycle nor avoidable GPU idle time is established by the timing totals.
- **Stages 2/3 plausibly add host synchronization cost**, but attributing the complete 151/168 ms differences to that fix is not justified by historical, differently instrumented controls and divergent generated tokens. Stage 3's contemporaneous 2K/128 pair loses only 1.19% TG.

### Unknown

- Which precise producer submissions were parked, already accepted by Vulkan, waiting on an earlier CPU output, or executing GPU work during each long wait.
- Whether the sampled alternating GPU activity reflects real serialization throughout the request; sparse utilization samples cannot reconstruct overlap.
- Whether identical configurations reproduce identical sampled IDs and logits on this build, and whether the missing probability entries are first-token/EOS/reporting behavior or a capture defect.
- Whether a smaller work queue improves total time, rather than redistributing waits or reducing useful overlap.

## 2. One next non-destructive experiment

**One diagnostic stage: a matched trace-OFF/trace-ON pair on the dev tree, with no algorithm, placement, queue-depth or synchronization changes.** This is a recommendation for ChatGPT to authorize, not an instruction I executed.

Use the exact Q4 model, four CPU banks 5/8/20/35, device mapping by PCI BDF, 16,384-token ID prefix/hash, context, q8 KV, batch 2048/ubatch 512, sampling, environment and request options from the handoff. Keep `TURBOPREFILL=0`. Use the same instrumented binary for both arms with tracing gated off/on. Run sequentially with fresh, equivalent cache/server state and record hardware conditions. Do not add `n_probs` to only one arm.

Keep the existing 32-token completion so this stage does not silently change server/request semantics; **turn tracing off at the prefill-to-decode boundary**. A proposed `n_predict=0` shortcut needs source verification that it actually evaluates the entire prompt, so I would avoid introducing it here. This remains a diagnostic pair, not a TG512 validation.

Use preallocated, bounded host-memory event buffers, preferably per thread, and dump after the timed request. No hot-path per-job printf, polling loop, extra GPU fence, GPU buffer or timestamp-query command. Capture overflow counts; overflow invalidates the affected reconstruction. Record the overhead of added host counter queries rather than assuming it is zero.

For each relevant input/worker job record:

- Request/split/microbatch ID, CPU ticket and execution mode; stable device BDF, queue ID, semaphore identity **and generation**, required value; D2H slot index/generation.
- Host monotonic times for input registration, job enqueue/dequeue, wait entry/exit, and release. At wait entry take one semaphore counter snapshot and queue-depth/running/sealed/signaled snapshot. Preserve the wait's return status.
- Producer context identity and its exact signal `(semaphore, generation, value)`: recording complete, parked, unparked, and **actual queue-submit entry and successful return** at Vulkan 3253. Log the submitted batch's wait dependencies as well as its signals, including CPU-output ticket dependencies where applicable.
- Existing park-mode transitions. Do not introduce a new `park(0)` merely to improve the trace.

Join exact producer records; a maximum submitted value is insufficient if records have gaps or submission order differs. Never compare numeric values from different semaphores/devices as though they were one counter. Account for a submission call spanning a wait-entry timestamp: a successful-return timestamp alone provides a bounded interval, not perfect knowledge of acceptance time.

**Discriminating outcomes:**

| Observation | Interpretation / falsifier |
|---|---|
| Input's producer is still parked when wait starts and is submitted later | Confirms delayed submission for that input; quantify the exposed delay before proposing scheduling changes. |
| Exact producer and its dependencies were already submitted; counter is below required value | Falsifies “this producer was never submitted.” Remaining candidates include GPU execution, queue dependencies and CPU-output dependencies; the counter alone does not distinguish them. |
| Worker waits on a producer whose dependency needs this same blocked worker/ticket to finish | Evidence for a dependency cycle, if all edges and identities are verified. Do not infer a cycle merely from a long wait. |
| Counter is already at or above the required value but the host wait interval is long | Investigate host scheduling, API/result handling and measurement attribution; do not call it pending GPU execution. |
| All long waits follow already submitted, necessary dependency chains with little idle opportunity | Defer queue tricks; focus subsequent work on graph cuts, placement or the real GPU critical path. |

**Stop/pass/fail:** preserve the existing fault/reset/OOM/headroom/process-error/user-cancellation guards and persist the exact stop reason. Use a progress watchdog that understands both prompt and generated-token progress; do not invent new timeouts or thermal thresholds. Preserve all clocks, voltage, fans, power limits and firmware/driver protections. Telemetry remains visible and durable.

A successful diagnostic has complete event joins, no dropped trace records, no new slot-lifetime behavior, matching prompt/settings and no changed outputs attributable to tracing. Retain the owner-approved performance floors: PP 287.73 and TG 24.797 against the stated baseline, and also compare the contemporaneous OFF arm. If the uninstrumented control is already below the floor or capture is ambiguous, report an inconclusive comparison and stop. If trace overhead breaches the gate, restore and stop; qualitative source findings may remain useful but the measured timing distribution is not a new performance baseline. No automatic 32K extension or functional patch in the same stage.

## 3. Why the depth-4 cap should wait

Queue depth 79 does not prove queue depth is the cause of 25 seconds of work. A cap can move the wait to the dispatcher, starve independent GPU submissions, or shift time back from checkpoints. “Largest drain under two seconds” is not a sufficient success criterion.

There is an additional source-level deadlock condition to preserve: the worker waits for `force || sealed >= ticket` before publishing outputs (CPU 350–354). `worker_seal()` advances only to the current `submitted` count (439–447), and the scheduler seals before entering the next graph compute. A newly enqueued job may therefore require later scheduler progress to be sealed. **Flushing parked GPU work alone does not prove that waiting for the oldest ticket to be signaled is safe.** Its output registrations must be complete and it must already be sealable/sealed, without requiring the blocked enqueue operation.

A later cap is justified only if the trace identifies excessive pending depth causing avoidable exposed delay or resource pressure, with independent work available, and a dependency-safe admission point. Count queued plus running jobs and their input reservations. Admission only after all D2H slots have been acquired may already be too late. Reserve resources at a well-defined split boundary; do not hold queue/slot locks while flushing or waiting. Measure whole-request PP, decode, total waits, overlap and ownership, not just smaller barrier timestamps. Four is a hypothesis, not an established optimum.

## 4. Safest lifetime design to investigate later

Do not preserve an unretired async copy because its fallback path happens to benchmark well. Preserve the efficient parts while making ownership explicit:

1. Give each graph execution/split a real input-ownership identity before async copy registration. A speculative `submitted + 1` worker ticket is not a complete owner for inline execution. Cover narrow inline execution **and wide graph-clone failure**: CPU 642–647 also falls back to inline after copies may already have been registered.
2. Retire only inputs owned by that execution. Establish producer submission and successful completion before the CPU reads their destinations. Releasing a slot does not replace waiting for its GPU writer or copying into the destination.
3. Where dependencies permit, wait once for the split's set of producer semaphores/values, then perform its required copies and releases. Coalescing to a maximum value is only valid within the same semaphore generation and a proven signal/order relation. Avoid the additional device-wide synchronize plus separate fenced read per tensor used by Stage 3.
4. Release staging slots exactly once after the GPU write and host consumption of that staging data finish. Keep CPU destination buffers alive through CPU compute, and output buffers alive through downstream GPU consumption. Releasing staging memory before matmul can be valid after the host memcpy; releasing the CPU input/output storage at that point is not.
5. Use generation-aware ownership against stale callbacks/ABA reuse. Cancellation, allocation failure, graph-clone failure, request reset and shutdown must account for pending inputs too. Never clear a busy bit to force progress while a GPU writer or callback can still reference it. Do not erase a shared future ticket's inputs merely because the current queue looks empty.

The current Vulkan wait callback discards the `waitSemaphores` result (17113). Error propagation belongs in a future correctness design: on device failure, “wait returned” must not become permission to consume stale data. I did not patch it here.

There is no way to remove a true GPU-to-CPU data dependency by relabeling it asynchronous. The realistic target is redundant global synchronization, duplicate submission/readback overhead, or earlier preparation of work that is genuinely independent. Stage 2 already performed scoped inline retirement; propose a specific reduction in that overhead rather than reimplementing it under a new name.

## 5. Alternatives ranked by evidence

- **Near term:** restore a trustworthy same-placement correctness reference with both pipeline/worker variables unset, then establish low-overhead native sampled-token capture. Diagnose actual submissions as above. Preserve the four-bank placement for these comparisons.
- **After diagnosis:** measure per-bank input-ready wait, CPU compute, payload and output-dependent GPU work. A placement experiment can prioritize expensive graph cuts or the slow riser transfers while satisfying each GPU's memory margin. Merely clustering CPU expert banks does not remove intervening GPU attention or automatically remove CPU/GPU round trips.
- **Later:** a single placement or microbatch-size change per paired experiment, if the trace shows these are on the critical path. Retain high-context PP and sustained TG as separate objectives.
- **Speculative redesign:** GPU-side expert-weight upload/preupload ideas such as PR #29963 change the architecture. They are not a demonstrated remedy for the present CPU `MUL_MAT_ID` pipeline. Strata's separate resident-expert TurboPrefill work is also not a drop-in patch for this Vulkan/Q4 setup.

## 6. Validation and report corrections

**Correctness and speed must have separate gates.** Neither readable prose, finite probabilities nor a matching first few IDs is a correctness pass. The baseline itself has a missing ownership path, so equality to its output is insufficient.

For a later validation stage, freeze the model fingerprint, binary and dependent-library hashes, four-bank placement, full effective environment, prompt ID array/hash, sampler and request options. Record tokens directly at the sampler/server's native token-ID boundary, including an explicit first-token/EOS accounting rule. Store sequence position, ID, finish reason and count in a bounded host buffer and flush outside timed sections. Do not reconstruct IDs by detokenizing and retokenizing, and do not substitute top-probability candidates for the sampled sequence. Verify the pinned server's API behavior before selecting an output option.

First repeat the same configuration to establish reproducibility. Compare the safe same-placement pipeline-OFF reference (both variables **unset**, not assigned `0`) with the candidate. For the first divergence, compare logits/top-1 margin under the **same forced token history**; continuing free generation after different tokens confounds all later comparisons. Add known-answer routing/reduction and retrieval tasks, then relevant reasoning tasks. Declare the numerical tolerance/quality criterion before evaluating a result; no silent relaxation after a miss.

Only a candidate that passes the agreed correctness gate proceeds to a paired TG512 experiment with identical capture overhead, warm/cold policy and high-context prompt. Use repeated, interleaved controls to estimate noise. Report PP wall, time to first token, timed decode count, decode wall, and end-to-end time separately. Longer tests remain separately authorized stages, not an automatic extension of the proposed trace.

Specific cautions in the originals:

- The reported TG values numerically use **31 timed tokens for a 32-token completion** and **127 for 128**: `26.102 × 1.18764 ≈ 31`; `25.379 × 5.004171 ≈ 127`. Confirm the API's first-token accounting. Thirty probability IDs still do not provide a complete 32-token sequence; do not guess which entries are missing.
- Stage 2's reported TG loss is **11.27%**, Stage 3's **12.37%**. The roughly 12.7%/14.1% figures are increases in decode duration, not throughput decreases. All still fail the stated floor.
- Stage 3's “2K OFF” means **bypass off with pipeline and worker still on**. It is not the original pipeline-OFF control. Its paired TG loss is 1.19%, whereas the 16K comparison uses the older control. Neither difference proves a universal per-copy penalty.
- Stage 1 already failed the TG instrumentation gate; added probability capture, tracing and different token trajectories are confounders. Do not attribute the whole 151/168 ms to a lifetime correction without a same-harness paired control.
- Stage 3 counts 128 activation plus 119 small bypasses at 16K. Assigning all 168 ms to “128 copies” ignores the small copies and other changed work. Stage 2's reported packed bytes and Stage 3's larger tensor spans should be reconciled using each tensor's shape, strides, logical payload and actual bytes moved before inferring bandwidth.
- Sixty-four busy slots at drain entry and 128 releases during the drain are not automatically contradictory: slots can be reused during a window. Use allocation/release event balances and generations rather than comparing those totals as static occupancy.
- A wrapper-level submit call and a device-accepted submission are distinct here. Timeline wait-before-signal is permitted by Vulkan; that alone does not prove a cycle. [Vulkan command-buffer specification](https://docs.vulkan.org/spec/latest/chapters/cmdbuffers.html)

## 7. Advice to ChatGPT as supervisor

Keep the 5% rule as the owner's **promotion/performance gate** until the owner changes it. A lifetime fix can pass a resource-ownership test while failing that gate; record both facts. Conversely, a leaky baseline does not become production-safe because a fix is slower. Recommend the correct same-placement pipeline-OFF mode as the reference and a possible conservative operational choice only after validating it; do not switch production without the required owner approval.

The next decision should be based on a trustworthy paired comparison: the actual correctness result, full TG512 cost, and any PP gain. Present that trade-off explicitly if a correctness fix remains slower. Do not override the gate, promote the baseline's apparent speed as correctness evidence, increase slot polling, disable checkpoints, combine a queue cap with a lifetime patch, or add an arbitrary temperature kill. No host-signaled GPU-event experiment or hardware reset belongs in this diagnostic stage.
