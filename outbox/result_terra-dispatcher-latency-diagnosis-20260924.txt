ROOT_CAUSES_AND_LOCATIONS:
1. Poll cadence and Git operations: TerraDispatcher.ps1 Get-Pending (around lines 89-128) calls Sync-Repo on every pass; Sync-Repo (60-71) fetches the main branch, and the main loop sleeps 8 seconds after each pass (around 438). Error and UI-wait paths also sleep 8 seconds (around 423-432). With successful network timing, this alone contributes roughly one poll interval plus the Git call, typically under 10 seconds.
2. Desktop foreground gating: Dispatch-TerraJob (around 204-257) checks for a quiet chat and a clear composer, calls ForceForeground, and waits if the exact Terra conversation is not foreground. The dispatcher can therefore wait while another window is active, the composer contains user text, or ChatGPT is still generating. The log records luna-window-not-foreground and composer-nonempty waits.
3. Strict serialization: Get-Pending excludes IDs already in dispatched state and results already present, and Dispatch-TerraJob calls Publish-LunaReply synchronously after sending. A slow job therefore blocks later inbox jobs until completion or timeout.
4. Response capture timeout and matcher: Publish-LunaReply (around 366-395) polls 40 times at 3-second intervals, up to about 120 seconds. It only accepts a fresh text node matching ^[A-Z][A-Z0-9_]{3,}$ and only when the UI no longer appears busy. Normal multi-line prose or a detailed report does not match this token-only expression, so a visible answer can still end as luna-reply-timeout. The two latest log entries show that timeout.
5. Narrow inbox discovery: Get-Pending scans only repo_cache\inbox\msg_*.txt and requires target:TERRA. It skips Tiel messages, already-dispatched IDs, and IDs with an outbox result. It does not scan prepared\ or the legacy inbox\chatgpt_message.txt path. During inspection, the repository's newest commit added a prepared\... file, which this dispatcher would not discover.
6. No restart supervisor: Startup\OrnithTerraDispatcher.cmd launches TerraDispatcher.ps1 hidden at user logon. This provides logon startup, not a service or watchdog that restarts the dispatcher if it exits. At inspection time status.json was updating, so the dispatcher itself was alive.
