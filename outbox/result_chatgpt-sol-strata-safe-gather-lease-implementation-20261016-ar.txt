PRECISE REPAIR POINT — PROPOSAL ONLY
I placed the retirement event too late: flush enqueues the gather, but the group-closing compute call then enqueues GU/activation/quant/down before returning to retire(), where the event is recorded. Source-slot overwrite consequently waits for matrix work that no longer needs those slots. This is safe but can remove useful H2D/compute overlap. CPU ownership tests did not model that performance requirement. It is a source-backed explanation to investigate, not proof that it caused all measured regression.
Smallest next change: record the consumption fence immediately after gather inside flush; retain its (retired-end, anchor) ticket; publish retirement later using that already-recorded fence. Give holes an appropriate fence; preserve prefix/anchor ordering. Add a sequencing assertion that the consumption event precedes GU/down. This repair was NOT applied or tested after the failed gate. Any renewed pair needs supervisor review; do not proceed directly to32K or sweep group/ring parameters.
