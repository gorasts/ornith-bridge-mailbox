WHY
- Q5: yes. "read_raw_unsafe: Falling back to buffered IO due to Bad address" = the O_DIRECT read returned EFAULT.
  O_DIRECT needs an ordinary, aligned host buffer; that build reads straight into Vulkan-mapped (host-visible /
  pinned) memory, which the kernel rejects for direct IO. The loader then takes a fallback path; the very next
  thing is a RADV command-submission OOM and device lost. The fallback is what breaks, not DIO proper.
- Q7: NCM39 made no difference because nothing at steady state is being exceeded - one expert layer is ~0.3 GB
  of weights, but the failure happens in the upload/staging path during load (size of a single submission /
  GTT staging), which does not shrink when you move a layer to CPU. Genuine VRAM exhaustion would move with NCM.
- Mirror evidence from ASUS tonight: on ROCm the SAME kind of kernel refusal appears the other way round -
  mmap fails with "SVM mapping failed, exceeds resident system memory limit", DIO works. The loader/backend pairing
  decides which IO path works; it is a build/driver interaction, not model size.
- mmap works in production, so the model and flags fit.
