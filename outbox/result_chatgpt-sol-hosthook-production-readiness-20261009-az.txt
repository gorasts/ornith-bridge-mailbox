# AZ: device-local host-hook production-readiness audit

**Decision: NOT READY for an environment-only production change.** The hook is present in the verified isolated Q4 build, but absent from the executable/modules selected by current three-card autostart. Adding `ORNITH_TP_PIN_DEVICE_LOCAL=1` to the deployed command would not install the missing scheduler gate or Vulkan allocator callback. No files, binaries, service state, model, or hardware settings were changed; `ornith-server.service` remains inactive.

The deployed command/config SHA-256s are `/etc/ornith/threecard.cmd` `e2169d06b50c7339c3f1ec71454ea0b4a4a99ea350e84be9bed0909ab8d85cc3`, `/usr/local/sbin/ornith_autostart.sh` `c1878c381d8e2b68fca999c54226cb643dcec71a1fe5a38944a2fde6980a8258`, and the service unit `5b75a8821b6be8b547bcc6e856c7bbf8846906ee42fbb98ee326301337eff1a4`. The service’s effective `ExecStart` is the autostart wrapper, with an `ExecStartPre` GPU UID verifier and multiple drop-ins. A `user-tuning-hold.conf` file exists, but the later `zz-user-autoselect.conf` clears `ConditionPathExists`; effective `ConditionResult` was `yes`. Preserve all these deployment controls and conditions as currently configured.

The deployed Vulkan and base modules contain neither `ggml_backend_tp_local_host_type` nor `ORNITH_TP_PIN_DEVICE_LOCAL` strings; the deployed `llama-tp-vulkan` source checkout likewise has no matching hook source. The isolated cachematched base contains the env-gate string and its Vulkan module contains the proc-address name. In that source, `ggml_backend_sched_tp_find_host_buft` checks `getenv("ORNITH_TP_PIN_DEVICE_LOCAL")`, then requests `ggml_backend_tp_local_host_type` from that backend’s registry. The Vulkan registry returns a device-context-owned host-buffer type. Since the check is `getenv` presence, even an empty value or `=0` enables it; OFF must mean the key is absent.

The production source checkout is at revision `10bf611e533d81f739128304991c5e133c6aebd8` but is dirty in backend headers/source, llama context files and server context, with additional local backup files. The exact source snapshot and build manifest that produced the October 6 production bundle are therefore **not established by this read-only audit**. Both bundles report the broad `libggml-base.so.0` SONAME, but they come from different trees/builds; SONAME agreement does not establish ABI or allocator compatibility. Do not copy a Vulkan or GGML library across bundles. The isolated test also used Haswell CPU code whereas deployment currently maps a generic CPU module. The measured gain cannot be attributed to an env toggle on the current binaries or generalized to the deployed IQ3 configuration.

## Evidence for benefit and deployment gates

On the matched 31,802-token Q4 task, the original AL pair measured hook ON 562.63 PP versus OFF 440.97 PP (+27.59%, ON first); reverse-order AY measured ON 564.422 versus OFF 441.568 PP (+27.82%, ON second). TG was approximately 27.5 in both arms, and all four answers passed the transaction oracle. This is credible evidence for that tested Q4/cachematched configuration, not a production IQ3 forecast or a general accuracy guarantee.

The constrained GPU0c minimum free memory was 324.5 MiB in both AL and AY—only 24.5 MiB above the existing 300 MiB guard. No faults were recorded. This margin is tight; there is no evidence here that the deployed model/settings or a 90K prompt would retain it. Do not change the guard or infer long-context headroom from this test.

The smallest responsible integration path, **only after separate owner approval**, is:

1. Recover and fingerprint the exact source/configuration used to build the deployed three-card bundle, including its local changes. Preserve the current `/etc/ornith/threecard.cmd`, autostart/unit/drop-ins, complete `build-vk/bin` module set and hashes as rollback artifacts.
2. Port only the scheduler env gate and Vulkan registry/device-local allocator callback to that exact source lineage. Build a wholly separate, versioned bundle; keep the current model and command flags, and keep all runtime libraries from the same candidate build. Verify the callback returns the requested device’s host-buffer type and matching allocator/free behavior; do not mix the cachematched Haswell modules with the production build.
3. Before any service activation, validate the candidate in an isolated instance using the deployed model/configuration with hook absent versus `ORNITH_TP_PIN_DEVICE_LOCAL=1` as the sole runtime delta. Check live maps, prompt/output correctness, grouped replay, real GPU faults, and the existing VRAM guard. The flag alone is not a valid test until the candidate contains both compiled pieces.
4. Require a successful exact 32K correctness/performance gate and measured per-card headroom above the existing 300 MiB guard before considering a 90K-context check. Treat 90K as a separate owner-approved gate; the 32K Q4 margin does not establish it. Keep temperature telemetry passive and firmware/driver protections intact.
5. Only after owner approval, activate by pointing the selected three-card command to the complete versioned candidate and adding `ORNITH_TP_PIN_DEVICE_LOCAL=1` alongside the existing TP setting. Rollback is to stop the candidate, restore the saved command/bundle selection and hashes, and leave the service inactive until explicitly authorized to restart. Do not edit production during this audit.

**Recommendation:** the hook merits a carefully staged port because the reversed paired Q4 result reproduced a material PP increase without a meaningful TG loss. Production integration is currently **NO-GO**: the selected stack lacks the hook, its exact build source is not cleanly attributable, and the deployed model/runtime differs from the measured setup. Proceed only with an owner-approved, isolated candidate build and the gates above; no production promotion is implied.
