# TurboPrefill and Strata: performance audit

14 October 2026. Based on Grok’s local OrnithBridge OUTBOX report and telemetry archive, the saved harness, a read-only source snapshot, and saved prompt/output tokens read over SSH. No inference or hardware tuning was performed during this audit.

**There is useful headroom, but low riser power alone does not establish a broken TurboPrefill implementation.** The best preset uses only one riser for prefill and gives it a limited subset of resident experts. The main GPU still controls each layer. The strongest opportunities are reducing primary-GPU memory/work, assigning more *profitable* resident work to peers, and removing redundant transfers. Several measurement and launch problems must be fixed before trusting further tuning.

## What the results establish

| Workload | Actual input tokens | PP tokens/s | TG tokens/s | Generated tokens |
|---|---:|---:|---:|---:|
| TP, 15K repeat | 15,000 | 232.7 | 24.1 | 128 |
| TP, 32K | 31,631 | 238.9 | 19.4 | 128 |
| Control, same 32K/chunk | 31,631 | 223.2 | 20.7 | 128 |
| TP, 64K | 61,629 | 234.2 | 23.5 | 128 |
| Latest nominal 88K retry | 91,627 | 234.4 | Not comparable | 2 |

The matched 32K comparison gives **+7.0% PP** and **−6.3% TG** in that sample. Other matched TP comparisons support roughly 7–12% PP gains. The larger overall improvement includes MTP weights moved to host memory, VRAM budgeting and larger prefill chunks. It cannot all be credited to TurboPrefill.

The latest 91,627-token run completed prefill, then emitted `user<|im_end|>` and ended. Its prefill rate is a usable partial measurement; its two-token TG number is not a sustained decode result. The session recorded a minimum 42 MiB of free VRAM with a warning-only guard, and the pasted telemetry reached 94°C junction. This is not a validated long-context operating point.

These runs use **ISTA IQ3_S**, not the UD-IQ3_XXS model from our earlier successful assignment test. They establish speed, not correctness or reasoning-token efficiency.

## Why the risers are lightly used

`STRATA_TP=1` selects CUDA1/0c only. CUDA2/0f remains available as a decode expert cache but does not perform TurboPrefill in this preset. `STRATA_TP=3` selects both; earlier dual-riser experiments are not a clean justification for enabling it on the latest configuration.

The apparent `layer_split: "17,34"` is **inactive metadata**. The harness adds `--layer-split` only when the config’s `gpu` list contains multiple entries; this config has `gpu: [0]`. Main-model layers therefore remain on GPU05. This can be a sensible architecture on slow riser links, but reporting it as an active layer split is incorrect. [S1, S2]

For each layer, the active peer receives the activations, computes routed experts already in its cache, and returns a weighted partial sum. By default it excludes experts already resident on the primary. It cannot run the next layer independently while the primary is still completing the current layer. [S2]

Saved utilization samples support the uneven-use observation:

| Run; samples filtered to main GPU ≥90% busy | GPU05 mean busy | GPU0c mean busy | GPU0f mean busy |
|---|---:|---:|---:|
| 32K TP; 21 samples | 99.0% | 24.5% | 1.0% |
| 32K control; 23 samples | 98.0% | 1.9% | 2.0% |
| 64K TP; 42 samples | 98.6% | 32.7% | 0.6% |

These are sampled utilization figures, not exact phase occupancy. The saved telemetry records the power *cap*, not measured power draw, so it does not independently verify the observed 20–60 W.

The older single-peer profiler shows roughly 5.0 seconds receiving inputs and 4.7 seconds returning outputs for a 7,494-token request. With width 2,560, 48 layers and FP16 in/out, that represents about **3.68 GB**, or approximately **0.38 GB/s during transfers**—consistent with the measured Gen2 x1 link. The peer can be idle much of the request while already reaching its link limit during transfer bursts. More arithmetic per transferred activation is the useful target.

## Concrete mistakes and limitations

1. **The “dequant” bottleneck diagnosis is not supported by that timer.** On the active MMQ branch, this bucket includes gathering packed quantized weights into group buffers. IQ3_S then uses quantized MMQ, which already handles quantization inside the multiplication path. The bucket can also span submission gaps. Treating its entire 34–37% as a removable standalone dequantization kernel is wrong. Measure packed gather, host submission gaps and MMQ separately. The cited timings are also older 7.5K requests, not the best 4096-chunk configuration. [S2, S3]

2. **The dual-peer timer mixes GPUs.** One `PeTimer` and event list are reused by both peer streams, with synchronization tied to the first peer. The dual logs report millions of milliseconds of idle time for requests lasting about 57 seconds. Those peer timing totals are invalid. Use one checked timer per device/stream and separate host wall-clock overlap measurements. HIP events measure progress in their recorded streams; they are not a substitute for a cross-device critical-path trace. [S2; AMD event documentation below]

3. **Saved environment settings are not reliably applied.** `guarded_speed.py` writes `STRATA_PREFILL_ISSUER=0` and `ARM_ENV` overrides into `config["env"]`. The benchmark calls `batch_test.Engine`, which constructs the environment from the inherited process environment plus `extra_env`, ignoring `config["env"]`. Thus the saved config does not establish that those overrides took effect. The inspected queue scripts do not explicitly export the issuer override; an inherited parent export remains possible. The source defaults to the threaded issuer when eligible. This also affects profiling switches supplied only through `ARM_ENV`. Merge config environment explicitly and record actual effective values. [S1, S2, S5]

4. **Long speed prompts contain repeated chat delimiters.** The 31,631-token prompt has one user start and one assistant start. The 61,629-token prompt has six starts, including repeated assistant prefixes embedded in the material; the 91,627-token prompt has ten. The 15,000-token prompt also repeats an assistant prefix. These are actual special token IDs, not merely quoted text. This confounds the short 88K output; it does not prove that prompt construction alone caused it. Rebuild long inputs from plain content and apply the chat template once.

5. **The TG and correctness evidence is insufficient.** Most runs decode only 128 tokens—roughly five to seven seconds. Different output trajectories and MTP acceptance rates confound timing. First-token top-logit agreement is not full-response correctness. The report already records later token divergence. Also, the wrapper hardcodes session metadata such as context 8192, prompt 7501 and limit 512, despite different actual arguments. Use the actual runtime settings and token counts. [S5]

## Highest-value improvements

### 1. Reduce primary-GPU intermediate memory and redundant work

The primary allocates `Dm` as `T × 10 × 2560` FP32 elements: **400 MiB at chunk 4096**. It still quantizes the full routed-row set, leaves remote-owned rows in this layout, zeros those remote results, combines the whole array, and then adds the peer sums. [S2]

Prototype compact local-row quantization plus group-wise weighted accumulation into a `T × 2560` sum. A single FP32 sum is **40 MiB**, although group scratch and synchronization buffers remain necessary. This is a concrete route to a smaller working set and less memory traffic; the net VRAM saving must be measured. It could improve prefill headroom and cache budgeting without increasing the chunk to 8192, which previously hung the GPU.

The peer already contains a related weighted-reduction design. Reusing the idea on the primary is more specific than adding another generic fusion layer. Preserve router weights and row ownership. Reduction order can change floating-point results, so deterministic reference comparisons and task correctness are required.

### 2. Give peers more useful work per transfer

Use a per-layer cost model: resident routed rows, avoided primary work, peer compute time, transfer cost and the primary’s remaining work. Skip peer dispatch when it cannot finish profitably; partition work so peers finish before the primary’s combine barrier.

For two peers, stage the common activation payload from the primary once where possible, then let each peer consume it with explicit lifetime/completion fences. The current path stages an activation copy separately for each peer. Group or tile pipelining is a candidate for reducing wait time, but must respect layer dependencies and the shared host/PCIe path.

Tune resident expert placement against representative prefill and decode routing separately. Blind duplication (`REMOTE_DUP`) consumes space that could hold distinct decode experts; Grok’s duplication experiments already showed no PP benefit and some TG loss. Likewise, `TAKE_RES` cannot offload an arbitrary primary expert: the peer must already hold its weights. [S2]

### 3. Optimize the measured packed-weight/MMQ path

After correcting instrumentation, determine whether packed-weight gathers, group padding/imbalance, host submission stalls or MMQ arithmetic dominate. Consider pointer-based grouped multiplication or a layout that avoids repacking resident weights. Measure the tradeoff before dedicating additional VRAM to prepacked duplicates.

Do not assume another “fused dequant” will eliminate the reported bucket: the current native IQ3_S path already dispatches quantized MMQ. [S2, S3]

### 4. Treat TG as a separate optimization problem

Decode already launches remote expert work before CPU pool work and waits afterward. `--remote-expert-opt` already supports reduced peer returns. Adding these mechanisms again would not be a new optimization. [S4]

Profile CPU expert misses, primary/peer cache hit rates, peer wait time, MTP draft time, verification time, accepted tokens per round and generated tokens per second. Optimize cache placement by **critical-path time saved per MiB**, not cache hit rate alone. Keep the MTP-host tradeoff measurable: freeing primary VRAM helped, but draft latency can offset cache gains.

Compare speculation disabled against the existing depths with the same workload. Use both fixed-token replay for hardware comparisons and ordinary generation for actual MTP throughput/quality. More accepted drafts are valuable only when their draft and verification cost pays back.

## Recommended implementation and validation order

1. Fix effective environment handling, actual-argument/session reporting, per-device timers, and prompt construction. Capture binary/source/config hashes and per-GPU memory budgets.
2. Establish matched controls on the **same IQ3_S model**, tokenizer, context, KV, prompt IDs and sampling. Keep hardware settings fixed. Separate TP off, first peer and both peers; use repeated runs with cooling/state recorded.
3. Validate TP against the control with fixed prefixes/logit comparisons, finite-value checks, deterministic toy cases for routing/reduction, and the earlier failed assignment task plus long-context retrieval. Keep correctness answers uncapped; use a separate sufficiently long decode workload for speed statistics.
4. Prototype compact primary intermediates and measure memory, PP, TG and correctness. Then test shared activation staging and cost-based peer assignment individually.
5. Tune decode cache placement and speculation only after stage timing is reliable. Reject gains that depend on reduced correctness, output truncation, faults or inadequate VRAM headroom.

**Expected scale:** the data supports real improvements, not a defensible 2–3× prediction. Going from 238.9 to 400 PP requires removing about **40% of total prefill time**. Merely activating the second riser does not establish that saving. Primary working-set reduction and eliminating avoidable work are the strongest routes identified here; their speedup remains unmeasured.
