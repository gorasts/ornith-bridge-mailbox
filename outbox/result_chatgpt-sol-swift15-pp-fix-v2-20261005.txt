# Swift 1.5 Q4_K_M PP investigation v2

## Executive conclusion

The current practical PP ceiling is confirmed at about **140-141 tok/s** on CURRENT GORAST. The best reproducible result was **141.255 PP tok/s** using the isolated `GGML_SCHED_MAX_COPIES=1` build, b4096/ub256. This is only **+0.83%** versus the matched stock b4096/ub256 result (140.088), so it is not a meaningful speed improvement. `RADV_PERFTEST=nogttspill` produced 141.224 PP, showing the result did not depend on GTT spill.

MAX_COPIES=1 reduced each Vulkan compute buffer from **93.09 MiB to 67.77 MiB** and the host compute buffer from **32.16 MiB to 11.79 MiB**, but recovered only **25.32 MiB** on the limiting GPU. That is far too little to solve the established 64K Q8 headroom failure. The required gates therefore correctly skipped the real 8K finalist and new 64K runs.

The MAX1 winner with `RADV_PERFTEST=nogttspill` loaded and completed: **141.224 PP / 13.157 TG512**, versus **141.252 / 13.153** without the environment override. Load and PP free VRAM were identical within measurement resolution. The result is not explained by GTT spill.

## Rejected and skipped results

- ub128 and ub64 were clean runs but rejected as candidates: 120.409 and 90.228 PP. The PP collapse as ubatch shrank established the bad direction.
- b4096/ub256 did not materially improve over b2048/ub256, so b8192 was not run.
- MAX_COPIES=1 did not meet the meaningful speed or memory-recovery gate. The real 8K F16/MTP6 validation was therefore not run; the canonical result remains **140.297 PP / 22.826 TG512**.
- No new 64K run was justified. The prior Q8/MTP6 load left about 50 MiB on 0f; applying the measured +25.32 MiB recovery would still leave roughly 75 MiB, about **325 MiB short** of the 400 MiB safety requirement. No rebalance or MTP7 was attempted.
- There were no crashes, OOMs, GPU faults, or contaminated measurements in this sequence.

## Remaining bottleneck and next engineering action

Batch and ubatch tuning, scheduler copy count, and GTT spill are not the main PP bottleneck. The 0.2-second activity trace shows long alternating stage activity across the x16+x1+x1 layer groups and almost no sustained three-GPU overlap. The remaining limit is pipeline scheduling and synchronization around the two x1 stages.

The single best next engineering action is to instrument Vulkan scheduler split/copy/event waits in `ggml-backend.cpp` for one 2K prompt, then remove the largest serialized wait or add safe stage overlap. More batch/ubatch sweeps are not justified by these measurements.
