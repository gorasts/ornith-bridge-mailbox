  Prod `1.05,1,0.85` = x16 0-14, riser 15-28, converter 29-39 + output.

## 5. Rules of thumb (Gorast + measured)

1. KV: **f16 > q8 > q4** - use the best that fits; q4 also lowers MTP acceptance on 3 cards (~0.72 vs 0.85-0.97).
2. MTP draft on the **LAST card**, ideally the fastest; with `MTP_SHARE_OUTPUT=1` and `-fit off`.
3. Buy VRAM with `-ub` (compute buffer scales linearly) before moving experts to CPU.
4. Experts on CPU in a GPU-only pipeline = PP collapse (streamed every prompt). In CPU+GPU setups they are the price of fitting.
5. Expert streaming (op offload) goes through the FIRST `-dev` device - put the x16 card first when experts live in RAM.
6. Measure TG with >= 1536-token answers (512 understates: tg_3s still climbing at 400 tokens).
7. Compare full-turn time (prompt + answer), not PP or TG alone.

## 6. Dead levers (measured, do not retry without a new reason)

ngram spec as default (task-dependent), threads 12 vs 14, huge pages, p-min, b/ub 4096, ik_llama (10x slower on qwen35moe Vulkan),
DRY sampler (doesn't stop loops), RPC draft (-10..16%), KV on CPU (-46% TG), draft on CPU (-39%), MTP depth >1,
`--ctx-checkpoints 0` (= noise, loses reuse), expert cache PR 27861 on single-card Q4 (no gain; needs >=16 slots),
REF timing (+1-3%), TurboPrefill (never active), userptr host import (TG -16%), x16 last at 131K Q4 with MTP (doesn't fit),
2 CPU expert layers to make MTP room (PP 411).

## 7. Traps (each cost runs)

- The progress line "1506 tok/s" is submit time; ~4 s pipeline drain follows. Use `prompt eval time`.
- Server with `-b 32768` prints no progress until the whole prompt is done -> watchdog must use elapsed time.
- `pkill -f` / `pgrep -f` with a pattern in the same ssh command line kills your own shell. Use PIDs or script files.
- Nested quotes through ssh mangle `\n` and quotes in patches -> always edit via a script file, compile before running.
- `-fit on` dry-runs the draft alone -> with MTP_SHARE_OUTPUT it asserts. Use `-fit off`.
- A delayed `kill -9 $(pgrep llama-server)` in a watchdog can kill the NEXT test's server - kill only the PID you judged.
- Watchdog must only judge a log written after the current server started.
- Vulkan ids != drm card ids; check bus ids. VRAM sysfs readings per card: `/sys/class/drm/cardN/device/mem_info_vram_used`.
- A riser card at 7866 MiB with 1.6 GB GTT is NORMAL in production (not a spill).
- After any GPU reset: HBM pin / REF drop -> `systemctl restart gpu-mempin` + verify.
- MTP correctness: compare answers with and without the draft on known-answer prompts before trusting speed.

## 3. Where decode time goes (the wall)

Decode window ~70-82 ms/token: **CPU expert work ~52 ms** (~2.75 misses/layer, AVX2 IQ decode ~0.55 ms/layer, compute-bound on 14
cores); GPU idles ~24 ms waiting for misses. Dense decode GEMVs ~235 GB/s (fine).
Measured no-gain: pool-workers 20 (=), 27 (21.5, worse), STRATA_MIRROR_THP huge pages (=), --spec 2 (25.1) / 4 (25.0) vs 3 (best).
Short turns: window path ~25 ms/token (23% cache hit, misses over x1 risers); `--short-read 64` right (160 worse).

## 4. Same lesson, different engines (what I realised)

1. **Expert streaming goes through ONE card - make it the x16 card.** llama.cpp op offload uses the first `-dev` device (x1 first: 18 PP,
   x16 first: 78-170); Strata's main GPU = x16. The 2-card Ornith Q4 run repeated it: converter first 299 PP vs x16 first 394.
2. **When experts are on the CPU, decode is CPU-bound** - Strata decode (52 of ~75 ms), single-card Ornith (GX build = +1-3% only),
   llama.cpp Flash-Next streaming (7.5 TG). Faster links do not help decode (converter: Strata unchanged).
3. **A profile bucket can be another device's wait.** Speeding one Strata kernel just moved time into "combine"; in llama.cpp the
   "1506 tok/s" progress number hid a 4 s pipeline drain.
4. **Chunk/ubatch size is the prefill lever in both** (Strata 2048 -> 8192 chunks; llama.cpp ub 512 -> 1024 + b 32768), and in both
   it is bounded by VRAM scratch (Strata: cache slots; llama.cpp: compute buffer = ub x ctx).
5. **Pinned / userptr host memory on ROCm/RADV gfx900 is dangerous**: Strata RAM arena + PLE-in-RAM wedged the box; llama.cpp userptr
   import cost 16% TG. Driver-allocated staging is the safe path.
6. **Tensor parallel over x1 links loses** (Strata TP helper made the primary wait; llama.cpp layer pipeline wins).
7. **gfx900 has no dot4 / fast bf16** - FP16 packed FMA paths win in both (STRATA_GX / STRATA_BF16_F16; GGML_VK_GX).

## 5. Safety rules (Strata on gfx900)

- Run every Strata test under `~/strata_fault_guard.sh` (patterns: IH ring overflow, restore_userptr_worker, qcm fence, unrecoverable,
  ring timeout, gpu reset, evict queues); it exits after firing - restart before each run.
- Never: RAM arena + `--ple-io ram`; pinning the 46 GiB mirror for a PCIe path (wedge risk).
- `GPU_PINNED_MIN_XFER_SIZE` must be set explicitly to 4096 (1000000 / 65536 -> HIP sees 0 devices).
- Drop page cache before Flash-Next start (TTM pool can hold 21 GB after many llama runs -> RAM check refuses).
- Safe reboot: `/usr/local/sbin/gorast_safe_reboot.sh`; verify boot time + undervolt after.
- Long-prompt hang (13 Oct, task 6 at token 15360, DeltaNet layer 8) - diagnose with STRATA_PF_STEP_SYNC=1 before 40K+ prompts.
