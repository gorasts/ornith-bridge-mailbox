The TP-associated memory delta stays nearly constant across these prompts, while longer-context runs reduce free VRAM similarly in OFF and ON: from 8K to 64K, OFF free space drops about 106 MiB/card and ON drops 106–109 MiB/card. This separates a roughly fixed TP-path footprint from a smaller context-length-associated increase; it does **not** identify the latter as KV versus activation/replay storage. Context capacity remained c131072, and the telemetry reports aggregate device memory only. Startup logs have replay markers but no per-allocation byte ledger.

Source makes the pinned-arena explanation plausible, but not exact: `ggml-backend.cpp` allocates scheduler arena blocks with a 128 MiB minimum (line 1253), tracks saved intermediate/input data in that arena (3738, 3832, 4748), and reserves 1.5× the measured series size (1282–1323). The measured extra 370.5 MiB on GPU05 and ~128 MiB on each other device are consistent with arena/staging allocations but cannot be mapped byte-for-byte to those calls from saved telemetry.

There is a specific source-level mismatch worth correcting before any performance claim about local pinning: `ggml_backend_sched_tp_find_host_buft` looks up `ggml_backend_tp_local_host_type` when `ORNITH_TP_PIN_DEVICE_LOCAL` is set, then falls back to the device's default host type if no hook exists (`ggml-backend.cpp:1191–1200`). The current Vulkan registry has `.get_proc_address = NULL` (`ggml-vulkan.cpp:20108–20113`), and its generic host-buffer allocator calls `ggml_vk_host_malloc(vk_instance.devices[0], size)` (`ggml-vulkan.cpp:16913–16930`). Thus this build cannot provide the requested per-device callback through that lookup; the flag alone does not prove device-local registration. This is a plausible explanation for remaining transfer waits, not proof that it accounts for the observed 128 MiB/card deltas.

Thermals: sampled junction temperature never reached 90 C. For the 64K TP-ON run, GPU0f reached 89 C; 14 samples (about 3.5 s total, longest consecutive run about 1.25 s) were at or above 85 C. The 31K ON peak was 82 C; 8K ON peak 74 C. So the recorded 89 C peak was brief and below the 90 C guard, but the thermal margin is small. GPU0c TP-ON free VRAM at 64K was 265 MiB—only 9 MiB above the 256 MiB floor. The 256 MiB sampled floor was not crossed, though the small margin is not a robust basis for extending context.

**Serialization and overlap:** Current replay logs at 8K/32K/64K report `groups=3 splits=18 saved=2/3 overlap=self-sync`. In `ggml-backend.cpp`, the group loop defaults to one step unless `ORNITH_TP_OWNER_ROUND` is set (4795–4808), synchronizes the group backend (4861), then dispatches each split in PREPARE_H2D → COMPUTE → STORE order (4863–4889). The host-mediated cross-backend copy explicitly calls producer `get_async`, synchronizes its event on the host, and only then calls destination `set_async` (1145–1152). Vulkan's async get path also falls back to sync-staging and `ggml_vk_synchronize` when `ggml_vk_buffer_read_2d_async` returns false (`ggml-vulkan.cpp:17171–17201`). These are clear possible serial boundaries; saved 64K logs do not measure how often that fallback occurs or its wall-time contribution.

The prior profile `/home/ubuntu/strata-tuning-20261007/ornith_q4_b10919_profile_on_20261008/criticalpath-summary.json` is from a different build/workload (8,215 tokens). It records 4.146 s of host-blocked wait on a 14.501 s prefill; GPU1/2 `get_async` blocked about 1.838 s for 71.432 MB and 1.306 s for 38.871 MB. Its trace counts 0.4235 s with at least two GPU compute jobs resident (2.92% of prefill), and only 0.000029 s with all three resident. “Resident” means submitted-to-completion queue residence and may include dependencies; it is not shader-active time. This evidence supports looking at host handoffs, but cannot be projected numerically to the Haswell build or 64K. No saved artifact proves concurrent shader execution on different GPUs.

**Ranked candidates**

1. **Test existing owner-round scheduling.** Observed: current mode is `self-sync`; source already has `ORNITH_TP_OWNER_ROUND` and interleaves one split per owner while retaining within-owner order (4803–4808, 4841–4864). Inference: this could keep another GPU's queue fed around owner handoffs and reduce critical-path idle time. It is not expected to save >128 MiB; allocation behavior should remain essentially the same. Risk is replay/state ordering correctness, so require readable output and fault/headroom checks.
2. **Implement/enable the missing per-device Vulkan host-buffer hook.** Observed: no proc-address hook is exported; generic fallback allocates through device0, and the prior different-build profile measured long GPU1/2 host waits. Inference: correctly registered per-device host buffers may allow the intended asynchronous path and reduce transfer stalls. No >128 MiB saving is established; allocation may move or increase. Risk is high if a buffer is not valid/pinned for the device that consumes it; do not use the unsafe async-upload path that produced slash-only output.
3. **Review arena reserve/lifetime after measuring actual allocation sizes.** Observed: arena reserves 1.5× series size and TP adds a stable ~128 MiB on each x1 device by minimum-free comparison. Inference: selective reuse or reclaiming inactive blocks might recover >128 MiB if a measured block is at least that large. No per-block accounting proves this today; reducing reserve without in-flight lifetime evidence risks memory corruption or faults.

**Single recommended next experiment (not run):** on the same Haswell binary, compare the current TP-ON `self-sync` mode with `ORNITH_TP_OWNER_ROUND=1` as the sole variable, using the exact 8,196-token prefix and B8192/UB2048, n_predict128. Use the existing non-serializing API + per-GPU queue-trace profile method from `host-pipeline-upstream/run_profile_on.py`, adapted only as a runner for this binary; do not use the Vulkan perf logger that forces graph fences. Capture API host waits, D2H/H2D bytes, GPU job execution intervals, and labeled GPU busy counters per BDF during prefill, alongside full response text/token IDs, faults, VRAM and temperatures. Count shader overlap only if active compute intervals/counters overlap across separate GPUs; submissions or queue residence alone do not qualify. Require coherent non-slash output, no faults, and >=300 MiB free on every GPU (hard abort below 256 MiB); report profile timings separately from throughput. This short test isolates whether the already-implemented owner-round schedule can create useful cross-GPU concurrency before any patch or longer context run.

Verdict: remain NO-GO for 90K under current memory/thermal margins. The clearest high-value code issue is the absent device-local allocator hook, but the safest next discriminator is owner-round profiling on 8K, not a speculative allocator change. No follow-up was run.
