EXECUTIVE CONCLUSION
No operator-cost result is reported because the existing Vulkan GPU timestamp profiler is incompatible with TurboPrefill's multiple in-flight command contexts. It owns one backend-level query pool and asserts that ctx->compute_ctx is expired at each profiled graph. TP intentionally retains/reuses outstanding compute contexts across pipelined split graphs, so the profiler aborts before it can safely produce timestamps. A request-gated retry reached requested=1 active=1, then failed on the first pipelined TP graph at the same guard. Inferring operator cost from CPU enqueue time would violate the task. A correct solution requires per-command-buffer query ownership and deferred result collection, which is a materially new >30-minute backend branch.

WHY THE SIMPLE PROFILER CANNOT BE PATCHED SAFELY
- Reusing the outstanding ctx->compute_ctx would mix commands from different TP graphs and make operator attribution invalid.
- Resetting the single query pool while prior submissions are pending is invalid.
- Forcing a global synchronize/submit before each graph would change TP scheduling, destroy pipeline behavior, and still misattribute commands already present in the context.
- Removing the assertion without changing ownership would risk query reuse, command-buffer lifetime violations, or corrupt timing.

SMALLEST SAFE PROFILING DESIGN (>30 MINUTES)
1. Add a profiling record to each in-flight vk_context/command-buffer slot, not ggml_backend_vk_context globally.
2. Allocate a dedicated query-pool range (or pool) per profiled TP graph/UB context: n_fused_dispatches+1 timestamps.
3. When split2/Vulkan2 graph recording begins, write a start timestamp and one timestamp after each fused dispatch. Capture immutable metadata per query: op type, fusion name, tensor name, parsed layer number when present, and UB/stage ID.
4. Attach the query allocation and metadata to the command context until its existing authoritative compute_done/event/fence completes. Never reset/reuse its queries while pending.
5. Collect query results only after the normal TP completion event is known complete; do not insert a new global wait in graph_compute.
6. Aggregate compactly by op/fusion and layer/group: calls, total GPU ms, mean GPU ms, and percent of split2 total. Record first/last graph timestamps to reconcile with the independently measured 363.778 ms service interval.
7. Use a bounded ring sized to the actual in-flight TP copies/UB slots; free query pools only after all associated events complete.
8. Gate collection to split2/Vulkan2 and the measured request so model load, reserve graphs, and other devices remain untouched. Split1/split3 totals can use start/end graph timestamps only.

LIFETIME / STORAGE CONSTRAINTS

- Query ownership must follow the same in-flight command-buffer/copy slot as activation storage; one global pool/index is unsafe.
- Result collection must respect Vulkan timestamp valid bits/period and handle fused dispatches consistently with existing vk_perf_logger naming.
